Before the models

Core concepts

Five ideas that decide whether a model is any good, whichever algorithm you use. Ten minutes here will make every model page clearer.

1. Features, labels and the two kinds of learning

A data set is a table. Each row is an example (a house, an email, an image). The columns describing it are features. In supervised learning one extra column is the label you want to predict: a number (regression, e.g. price) or a category (classification, e.g. spam or not). In unsupervised learning there is no label, and the goal is to find structure such as groups (clustering) or a simpler description (dimensionality reduction).

2. Never grade a model on its own homework

A model can memorise its training data, so its score on that data says little. Before training, set aside a test set the model never sees. Its score on that set estimates how it will do on new data. Every result on this site is a test-set score.

3. Underfitting and overfitting

A model that is too simple misses the pattern (underfitting). A model that is too flexible learns the noise as well (overfitting): it looks brilliant on training data and disappoints on test data. Every model has knobs that move it between the two, such as tree depth, k in KNN, or the degree of a polynomial below.

4. Cross-validation: a fairer score on small data

One test split can be lucky or unlucky. K-fold cross-validation splits the training data into k parts, trains k times, and checks on a different part each time. The average is a steadier estimate. It is also how hyperparameters are tuned without touching the test set. Press the button to step through the rounds.

5. Accuracy can lie

If 1% of transactions are fraud, a model that always says “not fraud” is 99% accurate and completely useless. On imbalanced data, look at precision (of the cases you flagged, how many were right) and recall (of the real cases, how many you caught). Set positives to 1% below and compare accuracy with the “always negative” baseline.

6. Leakage: the most common fake 99%

Leakage means a feature secretly contains the answer, for example a “cancellation reason” column when predicting churn, or a value that is only known after the outcome. The model scores near 100% in testing and fails in real use. If a score looks too good to be true, check whether one column alone predicts the label. The repository's automl.py does this check automatically.
